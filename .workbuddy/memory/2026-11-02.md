
## 渠道36 开放实际模型名（不再只能走 gpt-* 映射）
- 需求：用户想在别的 agent 里直接用 `deepseek-v4.1-flash` 等真实模型名，而不是只能填 gpt-6.1-sol。
- **关键坑**：只改 `channels.models` 不生效！New API 路由靠 **`abilities` 表**（group, model, channel_id, enabled, priority, weight），改完 models 后 /v1/models 不显示、调用报 `No available channel for model ... under group asxs`。
  正确做法：`channels.models` 与 `abilities` 两处都要写，然后重启 new-api 清缓存。
- 已验证可用的实际模型（上游 200）：deepseek-v4.1-flash、deepseek-v4.1-flash-sg、deepseek-v4-pro、glm-5.2、glm-5.3、glm-5.3-flash、minimax-m3.1-flash、kimi-k3.1-pro、hy4-preview、hy3。
- **上游无权限（已剔除）**：kimi-k3（model [Kimi-K3] service info not found）、kimi-k3.1-pro-highspeed、grok-4.7、gemini-3.8-flash（均 11158 类错误）。
- 渠道36 最终 18 个模型 × 2 组（asxs/c2a）= 36 条 abilities。入口模型 8 个（gpt-*）+ 实际模型 10 个。
- 计费核对：走入口 gpt-6.1-sol 与直接 actual name 都是 ratio 0.0685 / cache_ratio 0.02；直接调用时 logs.other.billing_model_name 为空（未发生映射），New API 回落到 origin model 计费，结果一致。
- 注意：token 18（GPT）有 model_limits 白名单只含 gpt-5.5，要用实际模型需先放开该令牌白名单。
- 待办：若后续再加模型，记得同时补 abilities，否则不生效。

## cli2api 容器 OOM 假死（500 upstream error: do request failed）
- 现象：New API 大量 `status_code=500, upstream error: do request failed`，集中渠道36；实为**请求发不到 cli2api**。
- 取证：`docker inspect` → **OOMKilled=true**，mem_limit 仅 1g；容器显示 Up 25h 但 `docker exec` 超时、3010 端口 000、日志停在 16:08（僵死近 1 小时）。
- 修复：compose mem_limit 1g → **2560m**，并加 `GOMEMLIMIT: 2200MiB`（Go 软限制，防硬撞 limit 被 kill），force-recreate。
  恢复后 cli2api 稳定在 1.87G/2.5G（75%），new-api 仅 98M，请求 200 ttfb 1.2s。
- 判断依据：cli2api 重启 40 秒即吃满 1.5G 并卡在天花板（Go GC 不主动归还），不是缓慢泄漏而是「能吃就吃」，1G 对 17 账号 + 高并发明显偏小。
- ⚠️ 宿主内存紧张：总 3.5G，cli2api 占 1.87G，可用仅 ~690M，swap 已用 1.2G/2G。cli2api 是最大内存户（LOG_MAX_ROWS=20000 + 多账号 worker）。
  后续若再紧张：① 降 CLI2API_LOG_MAX_ROWS 到 5000 ② 加 swap ③ 拆账号到第二实例。
- 教训：容器 OOM 后可能"假活"（Up 但不响应），只看 docker ps 会误判；要查 OOMKilled + 端口探测 + exec 是否可用。

## cli2api 内存真凶：qoder Node worker（非日志）
- 先按计划把 CLI2API_LOG_MAX_ROWS 20000→5000（request_logs 已裁到 5011 条），但**内存不降反升**（1.87G→2.26G），证明日志不是大头 —— 之前的判断错了。
- 真凶：**7 个 qoder 账号（全部 status=error）各自 spawn 一个 Node CLI 进程**，宿主 ps 显示 6 个 node 进程各 274~374MB，合计约 1.9G；而 qoder 近 6h 只服务了 **6 次请求**。
- 处置：通过 cli2api API `PATCH /api/accounts/{id}` body `{"enabled":false}` 禁用全部 7 个 qoder error 账号（无需重启）。
  效果：容器内存 **2.26G → 96MB（3.76%）**，node 进程 0，宿主 available 423M → **2463M**。
- 服务验证：ch36 请求 200 / ttfb 0.8~1.05s；近 3 分钟 34 次成功 0 失败；容器 healthy。
- 影响：qoder provider 的模型（deepseek-flash 等 qoder 版本）现在不可用。渠道36 映射全走 workbuddy/trae，不受影响。若要恢复需在控制台重新启用账号并重新登录。
- 结论：cli2api 的 OOM 不是"账号多"导致，而是 **error 状态的 qoder 账号仍保留 Node worker 进程**（未回收）。以后遇到 cli2api 内存高，先 `ps -eo rss,comm --sort=-rss` 看 node 进程数。
- 当前配置：mem_limit 2560m + GOMEMLIMIT 2200MiB（保留，余量充足）。
