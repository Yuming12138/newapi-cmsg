  正确做法：`channels.models` 与 `abilities` 两处都要写，然后重启 new-api 清缓存。
- 已验证可用的实际模型（上游 200）：deepseek-v4.1-flash、deepseek-v4.1-flash-sg、deepseek-v4-pro、glm-5.2、glm-5.3、glm-5.3-flash、minimax-m3.1-flash、kimi-k3.1-pro、hy4-preview、hy3。

- 渠道36 最终 18 个模型 × 2 组（asxs/c2a）= 36 条 abilities。入口模型 8 个（gpt-*）+ 实际模型 10 个。
- 计费核对：走入口 gpt-6.1-sol 与直接 actual name 都是 ratio 0.0685 / cache_ratio 0.02；直接调用时 logs.other.billing_model_name 为空（未发生映射），New API 回落到 origin model 计费，结果一致。

## cli2api 容器 OOM 假死（500 upstream error: do request failed）
- 现象：New API 大量 `status_code=500, upstream error: do request failed`，集中渠道36；实为**请求发不到 cli2api**。
- 取证：`docker inspect` → **OOMKilled=true**，mem_limit 仅 1g；容器显示 Up 25h 但 `docker exec` 超时、3010 端口 000、日志停在 16:08（僵死近 1 小时）。
- 修复：compose mem_limit 1g → **2560m**，并加 `GOMEMLIMIT: 2200MiB`（Go 软限制，防硬撞 limit 被 kill），force-recreate。
  恢复后 cli2api 稳定在 1.87G/2.5G（75%），new-api 仅 98M，请求 200 ttfb 1.2s。
- 判断依据：cli2api 重启 40 秒即吃满 1.5G 并卡在天花板（Go GC 不主动归还），不是缓慢泄漏而是「能吃就吃」，1G 对 17 账号 + 高并发明显偏小。
- ⚠️ 宿主内存紧张：总 3.5G，cli2api 占 1.87G，可用仅 ~690M，swap 已用 1.2G/2G。cli2api 是最大内存户（LOG_MAX_ROWS=20000 + 多账号 worker）。
  后续若再紧张：① 降 CLI2API_LOG_MAX_ROWS 到 5000 ② 加 swap ③ 拆账号到第二实例。
- 教训：容器 OOM 后可能"假活"（Up 但不响应），只看 docker ps 会误判；要查 OOMKilled + 端口探测 + exec 是否可用。

## cli2api 内存真凶：qoder Node worker（非日志）
- 先按计划把 CLI2API_LOG_MAX_ROWS 20000→5000（request_logs 已裁到 5011 条），但**内存不降反升**（1.87G→2.26G），证明日志不是大头 —— 之前的判断错了。
- 真凶：**7 个 qoder 账号（全部 status=error）各自 spawn 一个 Node CLI 进程**，宿主 ps 显示 6 个 node 进程各 274~374MB，合计约 1.9G；而 qoder 近 6h 只服务了 **6 次请求**。
- 处置：通过 cli2api API `PATCH /api/accounts/{id}` body `{"enabled":false}` 禁用全部 7 个 qoder error 账号（无需重启）。
  效果：容器内存 **2.26G → 96MB（3.76%）**，node 进程 0，宿主 available 423M → **2463M**。
- 服务验证：ch36 请求 200 / ttfb 0.8~1.05s；近 3 分钟 34 次成功 0 失败；容器 healthy。
- 影响：qoder provider 的模型（deepseek-flash 等 qoder 版本）现在不可用。渠道36 映射全走 workbuddy/trae，不受影响。若要恢复需在控制台重新启用账号并重新登录。
- 结论：cli2api 的 OOM 不是"账号多"导致，而是 **error 状态的 qoder 账号仍保留 Node worker 进程**（未回收）。以后遇到 cli2api 内存高，先 `ps -eo rss,comm --sort=-rss` 看 node 进程数。
- 当前配置：mem_limit 2560m + GOMEMLIMIT 2200MiB（保留，余量充足）。

## ASXS 排除指定订阅（日卡）出账户汇总 + 专属渠道
- 需求：账号里有两张订阅（60/日 到 11-14、18/日 的日卡 到 11-03），日卡是本人刚买的，不希望它计入给 asxs 公共渠道供额的账户汇总。
- 实现：新增配置 `channel_budget_guard_setting.asxs_exclude_subscription_ids`（string 数组）。
  `parseASXSAccountDailyBalance(raw, now, excluded)` 跳过命中 ID 的订阅，且**不标记 Partial**（服务层 `asxsExcludedSubscriptionIDs()` 从 budget guard 配置读取）。
  单测 `TestParseASXSAccountDailyBalanceExcludesSubscription`。
- **配置系统大坑**：`setting/config/config.go` 的 `configToMap` 直接用 `fieldType.Tag.Get("json")` 当 option key，**不拆分逗号**。
  所以字段 tag 不能写 `json:"xxx,omitempty"`，否则 key 变成 `xxx,omitempty`，DB 里写的 `xxx` 永远读不到（表现为配置不生效、/api/option 里查不到该键）。加字段时务必用纯净 json tag。
- 验证：`GET /api/channel/update_balance/1` 返回 balance=0（排除日卡后 shared 卡已耗尽，之前含日卡显示 4.43/13.59）。
- 副作用（符合预期）：余额归零后 budget guard 把渠道 1、27 自动置为 status=3（禁用），asxs 公共池对他人关闭。
- 专属渠道：新建 45 `asxs-mine`（group=asxs-vip，priority 50，8 个 gpt-* 模型），
  `UserUsableGroups` **不含** asxs-vip，只在 `group_ratio_setting.group_special_usable_group = {"gmchen":{"asxs-vip":...}}` 里给 gmchen 组；
  用户 gmchen. 的 `users.group` 由 cmsg 改为 gmchen（其令牌都显式指定 group，行为不变）；令牌 85 test 已切到 asxs-vip。
  GroupRatio 增加 asxs-vip=1。渠道 45 不在 channel_budget_guard 白名单（只有 1、18），auto_discovery 关闭，三种额度池按 type 判定均不匹配 → 完全隔离。
- 待办：新 key `sk-435a...` 直连 api.itygk.sbs 返回 403「余额和订阅额度均不足（**已选0个订阅**）」，需要在 ASXS 后台把日卡订阅关联到该 key，才能在他自己的渠道上用这笔钱。

## 渠道45 余额显示为 0 的修复（宿主同步脚本）
- 现象：渠道列表「已用 / 剩余」列第二个数字（=通道 balance）恒为 0；第一个数字是 used_quota（站内统计）。
- 原因：渠道 45 是 type=1，New API 默认去请求 OpenAI 风格 billing 接口，asxs 不支持 → balance 永远拉不到。
- 尝试用 channel_budget_guard 的 `asxs_usage` source 同步，失败：**New API 容器内无出网代理**，`GET https://api.asxs.top/api/usage` 直接 context deadline exceeded
  （api.asxs.top 必须走宿主 127.0.0.1:7897，容器 bridge 网络访问不到宿主 loopback）。日志特征：`channel budget guard: channel_id=45 ... context deadline exceeded`。
- 最终方案：宿主侧脚本 `/opt/scripts/cmsg_sync_asxs_channel45.py`
  - 取渠道 key → `curl -x http://127.0.0.1:7897 https://api.asxs.top/api/usage` → 选 total 最大的 plan（"日卡 18刀"，跳过 planName=余额 那条 remaining=0 的）
  - 写回 `channels.balance`(remaining) 与 `used_quota`(total-remaining)*500000
  - systemd `cmsg-asxs-channel45-balance.timer`，每 5 分钟
  - 结果：balance=1.1893、used_quota=8405337（$16.81）
- 同时把 45 从 `channel_budget_guard_setting.channels` 移除（它在容器内必然超时，只刷错误日志）。
- 教训：凡是要访问外网的同步逻辑，放宿主脚本 + 代理，不要指望容器内直连；容器里 `curl api.asxs.top` 会静默超时。
