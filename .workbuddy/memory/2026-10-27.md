## 图片输入 400（11101 invalid image_url content）（2026-10-27 15:34，已修复上线）
- 现象：ch36 报 `status_code=400 {"code":11101,"msg":"Parse message failed: invalid image_url content at index 2: json: cannot unmarshal string into Go value of type ***.ImageContent"}`。
- 根因：Codex 的 `input_image` 里 `image_url` 是**字符串**（Responses API 风格），而 Chat Completions 要求 `image_url` 是对象 `{"url":...}`。转换器 `responsesImagePartToChatImageURL` 把字符串原样透传 → cli2api 解析失败。此前桌面端没报是因为之前根本没走到图片分支（工具都丢了）。
- 修复（`ed53ffb`，已部署 `new-api-ed53ffbf2e7f-image-url-object-20261027153300` 并 push）：字符串包成 `{"url":...}` 并带上 `detail`；`url` 键为字符串时同样包裹；已是对象则原样透传。实测 1×1 data-URI PNG 请求 200，模型正确识别纯色图。
- 教训：**转换器对 Responses 字段不能原样透传，凡是 Chat 侧有结构要求的都要归一化**。同类隐患可再排查 `input_file`（file 字段结构）。

- 根因（**关键缺陷，影响所有多轮工具会话**）：Codex 把每次执行结果以 `{"type":"custom_tool_call_output","call_id":...,"output":[{type:input_text,text:...}]}` 回传，而转换器 `responsesInputItemToChatMessages` **没有这个 case** → 掉进默认分支变成空 user 消息，**工具输出全部丢失**。模型看不到自己命令的结果，只能反复重查。另外历史里的 `custom_tool_call` 被转成 `type:"custom"` 的 tool_call，上游同样不认识。
- 修复（`745c458`，已部署 `new-api-745c458193d3-custom-tool-output-20261027154400` 并 push）：① `custom_tool_call_output` → `tool` 角色消息（call_id 对齐，output 内容数组展平为纯文本）；② 历史 `custom_tool_call` 重包成 `{"input": "<原文>"}` 的 function 调用，匹配上游的函数 schema。
- 验证：直连 cli2api 确认 `tool` 角色消息**能**透传（对照 system/developer 会丢）；实机重跑同一任务，一轮产出 `E:\Playground\pelican_bike_animation.html`（22.7KB，含 svg/animate/requestAnimationFrame），81.6k tokens 完成，DSML=0，无死循环。
- **Codex Responses 请求里已知的全部特殊 item 类型**（转换器必须逐个处理，不能落默认分支）：`message`、`function_call`、`function_call_output`、`custom_tool_call`、`custom_tool_call_output`、`additional_tools`、`reasoning`（默认分支会把它当 user 空消息，好在 Codex 不回传 reasoning）。

## 渠道36 (cli2api) 429 "cooling down on all available accounts" 机制
- 表现：New API logs type=5，content = "status_code=429, model deepseek-v4.1-flash is cooling down on all available accounts"。
- 根因：workbuddy 上游对单模型做**每日用量频控**（code 6004 "usage exceeds frequency limit ... reset at 2026-10-28 00:33:28 UTC+8"）。cli2api 按 **(account, model)** 粒度写 `account_cooldowns`（列：account_id/model/down_until/backoff_level/kind/message/model_kind），选号阶段发现全部账号都冷却就直接 429，**不发上游**（故 request_attempts 无记录）。
- 不是特定用户的问题：4 小时内 429 次数 zcy 13 > cj 11 > gmchen./Hufulin 3 > Tz 2。截图看起来"只有 cj"是采样偏差 + 失败者才会重试（重试者悖论）。
- 为什么同一秒别人成功：健康账号被 zcy 的连续大请求（每 ~13s 一发、196k prompt tokens）占住槽位，此刻到达的请求（cj 的重试，间隔 24-45s）全部撞冷却 → 429；19:08 后 zcy 节奏放缓，槽位释放，cj 立即恢复。
- 消耗分布（3h, deepseek-v4.1-flash）：acc_92e8 54.5M tokens、acc_d182 99.5M tokens —— 这两账号已冷却到次日。
- 治理方向（未实施，待主人定）：
  1) 把 c2a 分组部分模型映射从 deepseek-v4.1-flash 分散到 -sg / 其它模型（上游错误里自带 "switch to the other models" 建议）；
  2) routing_strategy 现为 fefo（优先吃临期套餐，会集中流量）→ 可评估 round-robin 打散；
  3) 客户端侧降低失败重试频率。
