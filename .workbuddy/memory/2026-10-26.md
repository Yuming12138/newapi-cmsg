## gemini 频繁 429「Individual quota reached」诊断与处置
- **现象**：渠道 35 (gemini-CPA) 走 /v1/responses 约 45% 请求 429 `Individual quota reached. Please upgrade your subscription... Resets in 48h32m8s`；用户看 HMC 配额面板以为额度充足。
- **根因两层**：
  1. antigravity 的配额分 **3p（Claude/GPT）** 和 **gemini** 两套独立窗口。HMC 配额卡片只显示「Claude 和 GPT 模型 / Weekly Limit Remaining」，而 claudecisilva643 的 **gemini weekly 已 100% 耗尽**（reset 2026-10-28 14:45 UTC，与报错的 48h32m 完全对上），natahsanora996 的 gemini weekly 仅 58%。面板看的是另一个窗口 → 误导。
  2. v8 `sdk/cliproxy/service_config.go:345` 的 `forceHomeRuntimeConfig` 在 home 模式**硬置 `DisableCooling=true`** → 429 凭证永不降温 → CPA 继续把约一半 gemini 请求发给烧穿账号。24h 实测：19 OK / 16× 429 quota / 4× 429 resource / 1× 499。
- **处置**：直接 UPDATE home.db `auth` 把 claudecisilva643 置 `disabled=1, status='disabled'`（Home 每 ~10min 重读 auth 索引会自动生效，无需重启；比 HMC 快，因为 Home 自身管理密钥不在服务器上——DB config 里的 `remote-management.secret-key` 是给 CPA 节点用的，调 Home 管理 API 返回 `invalid management key`）。处置后连续 6 次 gemini 请求全成功。
- **剩余容量**：仅 natahsanora996 一个免费版账号可用，gemini weekly 58%、reset 2026-10-29 11:34 UTC。到期前若继续按现速率消耗可能触顶；根治需加号或升级套餐。
- **待办**：claudecisilva643 窗口 2026-10-28 22:45 CST 重置后可重新启用（UPDATE 回 disabled=0 或 HMC 操作）；建议后续给 quota guard 加「weekly 100% 自动 disabled」逻辑，避免此类问题复发。

## 二次修正：禁用必须改 auth_json 内部字段（否则 Home 照旧下发）
- 现象：只把 `auth` 表的 `disabled` 列置 1 + 重启 CPA，仍然 429；usage 显示失败全是 `auth_index=a447a2f4`（claudecisilva643），成功全是 `0a8e8c25`（natahsanora996）。
- **根因**：Home 下发给 CPA 的是 `auth_json` 序列化内容，其中的 `disabled/status` 内部字段仍是 `false/error`；表列只是索引/查询用，不参与下发。所以必须同时改 **auth_json 内的 `disabled: true` + `status: "disabled"`**，并 `version=version+1`，再 `systemctl restart cmsg-home` 让它按新内容重载并下发。
- 验证方法：`SELECT substr(timestamp,12,8), failed, fail_status_code, substr(auth_index,1,8) FROM usage ORDER BY timestamp DESC LIMIT 8` —— 修复后应只剩好号的 auth_index。
- 结果：修复后 10/10 成功（6 次即时 + 4 次延迟 100s 复测），无反弹。

## 根治：打开 Home 的配额降温调度（不再手动禁用账号）
- **根因**：生产 `config` 表 `disable-cooling=true`（遗留自上代配置）+ 两个 antigravity 账号的 `attributes/metadata` 各自带 `disable-cooling=true` 覆盖。Home v1.1.5 文档明确：`cooldown.disable-cooling` 是「**Home request-error and quota cooldown scheduling**」总闸——关掉它，Home 就不再按配额窗口排除烧穿的凭证，于是继续把一半 gemini 请求发给死号。CPA 侧 `forceHomeRuntimeConfig` 强制 `DisableCooling=true` 是**设计如此**（注释：Home owns cooldown decisions），不该在节点侧改。
- **修复**：① `UPDATE config SET value='false' WHERE key='disable-cooling'`；② 两个账号 auth_json 的 `attributes['disable-cooling']='false'`（**attributes 必须是 string 值 map**，写成布尔会让 Home 迁移报 `json: cannot unmarshal bool into ... type string` 而启动崩溃）；③ 重启 `cmsg-home`（必要时再重启 CPA）。
- **效果**：把 claudecisilva643 重新启用（disabled=0）后，连续 10 次 gemini 请求**全部命中好号、零 429**；Home 按 `quota_window.status=exhausted` 自动排除，窗口 10-28 22:45 重置后自动回归，**无需再手工禁用/启用**。
- **不再需要**：手动改 auth_json 禁用那条路（只作为应急手段保留）。也说明前一轮「重启 CPA 才生效」的现象是 disable-cooling=true 下 Home 不排除的副作用。
- 副作用/权衡：transient 429（No capacity）现在会让凭证降温 60s，单号时可能短暂全断；比 45% 持续失败好。
- 事故记录：改 attributes 用布尔值 → Home 迁移失败、服务起不来（约 1 分钟）；已修为字符串。备份在 `/opt/cliproxyapi-home/backups/before-enable-cooling-20261026/state.json`。
- 另：token `lap`（id=67）所属用户余额被测试打到 $0（New API 侧「用户额度不足」）；token 95 仍可用。
