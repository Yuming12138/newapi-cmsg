## hy4 上下文实测：200K 是保守值，实际 ≥1M
- catalog 报 `catalog_context_length: 200000`、`context_editable: false`、`max_output_tokens: 64000`。
- 实测（直连 cli2api，model=hy4free）：
  - 216K tokens（1.48MB payload）→ **200**，23.4s ✅
  - 1045K tokens（3.99MB payload）→ **200**，60.6s ✅
  证明上游上下文远超 200K，catalog 的 200K 是保守值。
- 尝试覆盖元数据失败：写 `model_settings`(hy4free/hy4std → 1000000) 后重启，`/v1/models` 仍返回 200000
  —— `context_editable=false` 时 cli2api 不采纳 model_settings 覆盖（catalog 是权威值），已回滚这两条记录。
- 影响评估：请求本身不受 200K 限制（1M 能过）；但 `/v1/models` 元数据仍报 200K，若客户端按元数据硬卡长度会受限。
- 另注：1M tokens 单次请求耗时约 60s，客户端超时设置要跟上。

## 渠道27 峰谷倍率定价（自研渠道级倍率）
- 需求（北京时间）：23:00-08:00 = 0.25x、08:00-14:00 = 0.55x、14:00-18:00 = 0.50x、18:00-21:00 = 1.00x、21:00-23:00 = 0.55x。
- 背景：New API 原生**没有渠道级倍率**（只有 `GroupRatio` 分组倍率 + `GroupGroupRatio` 用户级），改 GroupRatio 会波及 asxs 分组下所有渠道，所以自研。
- 实现（commit `28b8b37`）：
  - 新 `setting/ratio_setting/channel_peak_valley.go`：读 option `ChannelPeakValleyRatio`（channelID → 时段数组），按 `time.FixedZone("CST", +8)` 实时计算；支持跨天时段、to 端排他；未配置/配置损坏/其他渠道一律返回 1。
  - `relay/helper/price.go` 的 `HandleGroupRatio`（两条计费路径 `ModelPriceHelper` / `ModelPriceHelperPerCall` 共用）末尾乘上渠道倍率，用 `common.GetContextKeyInt(ctx, constant.ContextKeyChannelId)` 取渠道。
  - **按请求实时计算，不需要定时任务**；option 由 `model.loadOptionsFromDatabase` + `SyncOptions` 自动同步进 `common.OptionMap`（任意 key 都会写入）。
  - 单测覆盖 12 个时段边界 + 未配置/损坏配置回退 1。
- 部署：release `new-api-28b8b37-peak-valley-20261104185115`，option 写入 DB，重启生效。
- 验证：临时探针给 27=0.9、36=0.8 → 走渠道36 的请求 `logs.other.group_ratio=0.8` ✅，证明按渠道区分生效；随后恢复正式配置，当前 18:00-21:00 段 group_ratio=1。
- ⚠️ 重要：实测 token 4 和 token 22 的请求**都走渠道 36**，几乎没落到 27。峰谷倍率虽已生效但可能收不到流量；若要真正起效需调整 27/36 的 priority/weight 或把 36 也纳入时段表。
- 注意：预扣费与结算若跨时段边界会用不同倍率，New API 走多退少补。
- 更正（11-05 00:20 用户确认）：峰值时段实测流量不走27 只是当时（18 点）的路由快照；谷段 00:20 的日志确认 Mao/Maoyan 请求确实走 **asxs-5x(27)**，前端在分组后显示 `asxs · 0.25x`，峰谷倍率已生效并可见。此前"流量几乎不走27"的担心不成立，无需调整 27/36 优先级。
